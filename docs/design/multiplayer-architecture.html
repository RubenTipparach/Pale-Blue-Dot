Multiplayer Architecture

How one planet is shared by up to 8 players: one server owns everything that is saved, each player's game builds its own view of the world, and per-region checksums keep every copy honest. This is the plan in openspec/changes/multiplayer, drawn out. Nothing here is built yet.

"server authority - server contains all data on item locations, map changes etc. ... a player interacting on one side of the planet with another player on other side of the planet, server must mediate that. each player handles their own LOD local data. sever periodically sends out checksum for the "chunk" client compares, and request new data if the "chunk data doest match"

the owner, 2026-11-18

01The shape: one server, many views

The server holds the one save. A game never writes the world. It sends what its player tried to do, and changes its own copy only from what the server sends back. What the server sends is facts (edits, records, items), never geometry: each game builds its own detail tiers, contact and light from the seed plus those facts, the way it already does today.

02Single player is the same server

There is no single-player path and a separate network path that drift apart. Single player starts the server inside the game process and talks to it through an in-memory channel carrying the same messages as the socket. Hosting opens that running server to other players without a reload. A dedicated server is the same crate with no window.

03A dig, from click to everyone

The player's own click stays instant: the game runs the same accept rule locally and draws the result at once, marked provisional. The server decides for real, writes it to the save, numbers it, and sends it to every player near that region in that order.

04Near and far

The "chunk" is the region already planned for saving and loading: a level-5 triangle of the icosahedron, 20,480 on the planet, each about 180 m across and about 2,000 hex cells. Each game subscribes to the regions its detail tier can reach, plus a margin ring. Players whose rings overlap share the same ordered stream. Players on opposite sides share nothing but the server.

One cost of this, accepted for the phase: a large build on the far side does not show in another player's far terrain until they come near, because the far terrain comes from the seed alone. A small per-region summary for the far view (height change, lamp count) is a named follow-up.

05Checksums and resync

The server sends each subscribed region's sequence and digest every few seconds, round-robin, and on every new subscription. The game digests its own copy at that sequence. If they differ, it asks for the region and replaces its copy with the server's snapshot, which is the same bytes the save writes for that region.

What a region's digest covers, in this order, so every machine hashes the same bytes:

  • its terrain edits, by cell key ascending, each cell's layers in the order they were made;
  • its water cells (level and flags), by cell key and layer;
  • the records in it (dropped items, chests, crops, animals, lamps, stations), by record id.

The hash is a fixed 64-bit FNV-1a, written once in pbd-core with a pinned test value, so it is equal on every operating system and processor. It is kept up to date as changes apply, so a check is a lookup, not a pass over 2,000 cells. Drawn things (columns, light, GPU data) are never hashed: they follow from the facts, and the join check makes sure every game builds them with the same generator.

Positions sent between machines are body-relative f64, the same form a save stores. Each game converts them into its own floating origin when they arrive, so one player's origin shift never moves anyone else.

07Joining, and saves

  • Join check. Protocol, topology, generator and content versions and the world's identity must all match. If one differs, the join is refused with a short message such as "Game version differs" and nothing else is sent.
  • Loading. The player's record, the clock and the regions around them arrive first; the loading screen stays up until those and every render pipeline are ready, as the boot does now.
  • Old saves. They open and host unchanged. The host is player 0, which is what the save's player token already means. Each guest is a new player record (pack, position, missions), added without touching anything already there, and the world still opens alone afterwards.

Luanti has no checksum. It trusts reliable delivery plus resend-on-refuse, and cannot notice a copy that drifted silently. The region digest is the safety net it lacks, and it can run slowly because resend-on-refuse catches the common case first.

10Not in this phase

  • PvP and damage between players; claims and permissions beyond kick, ban and rate limits (they come with building).
  • More than one person aboard a moving craft (once vehicles and ships exist).
  • Server lists, matchmaking, relays for players behind routers, and voice. LAN and direct address first.
  • More than 8 players.
