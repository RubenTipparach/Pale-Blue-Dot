Performance suite · A/B

lighting-model: today against new

Apple M4 Max (Metal), release build of b85718f (the tree's later edits were docs, tooling and unbuilt code; the exe is that commit's), window 1440 x 900, uncapped (--no-vsync), clock pinned at 10:00, first 10 s of each run thrown away. Three scenarios: clouds (--route scenic), storm (--route scenic --rain 1) and walk (--walk-distance 1000). Each variant ran twice, interleaved, with the screen unlocked and every GPU app closed (Steam, Chrome, Spotify, VS Code; owner: "close out any apps using the gpu before doing your run"). All 28 runs were valid.

The owner's targets are 120 fps (8.3 ms) at the 95th percentile and never below 60 fps (16.7 ms) at the 99th.

Findings

  • The new model costs about 4.1 ms at p50 in flight and 1.6 ms on foot. Clouds 15.9 -> 20.0 ms, storm 15.5 -> 19.6 ms, walk 10.1 -> 11.7 ms. The spread between a variant's two runs is 0.2 ms or less on most flights, 0.8 ms at most (today's clouds), and 0.7 / 1.1 ms on the walks.
  • L8 (reflections) is the one part that costs measurably: 1.3-1.9 ms at p50 (clouds 20.0 against 18.1, storm 19.6 against 18.3), and most of the tail: p99 about 55 against 47 ms. It is the first place to tune.
  • L3 (soft shadows) and L4 + L7 (sun bounce, lamp bake) cost nothing measurable: within 0.3 ms of new, inside the spread, on both flights.
  • Our bloom costs 1.5-2.2 ms at p50 (21.6 / 21.8 against 20.0 / 19.6). It stays off by default on a Mac; Settings turns it on.
  • The storm costs no more than the clouds with the new model: the wet film and the lit rain fog are inside the spread on these flights, which see wet ground only from far off.
  • On foot the new model's tail is 2-3 ms longer: p95 / p99 13.5 / 16.2 today against 16.2 / 18.0 new. The walk is CPU-bound enough that a busy machine moved it (see above).
  • About 6% of flight frames are spikes, and most are paired with a short frame (a 30 ms frame then a 2 ms one, summing to about 2.2-2.6 frames): presentation pacing, the CPU waiting for the next drawable, not work. Today's model shows the same share; the new model makes each stall longer because its frame is longer on the GPU. The rest (10-30% of spikes) sit near terrain landings and the town bake.
  • Every scenario misses the owner's budgets (p95 8.3 ms, p99 16.7 ms) with both models on this machine, as today's model already did.

How this was measured

  • One machine, one sitting. Separate sittings on this Mac differ by more than the in-sitting spread (today's walk: 9.0 ms in a run cut short earlier, 10.1 here), which is why only interleaved variants are compared.
  • On this Mac the "GPU clouds" column spans more than the cloud passes (it rises 4 ms with lighting changes that touch no cloud pass); read it as GPU time up to the composite. "GPU total" is not reported on Metal.
  • The walk's stuck-handling tapped the dig button rather than holding it (owner: "gotta hold mouse down to break blocks"), so a stuck walker never dug out; it is fixed after this sitting, which makes later walks not comparable with this one.
  • The CSVs and logs are local (output/perf/2026-10-29-clean).

Each run starts from a fresh world with the clock pinned at 10:00 and throws away its first 10 s. A cloud run that never found cloud, or a route that never landed, is marked invalid and left out. Traces are binned to 0.1 s: the faint line is each bin's worst frame, the solid line its median. Reproduce with:

python tools/perf_suite.py --scenarios clouds,storm --repeats 2 --out output/perf/2026-10-29-clean-full --variant "today||PBD_LIGHTING=today" --variant new --variant "no-L3||PBD_SOFT_SHADOWS=0" --variant "no-L8||PBD_REFLECT=0" --variant "no-L4-L7||PBD_BOUNCE=0;PBD_LAMP_BAKE=0" --variant "bloom-lite||PBD_BLOOM=lite"
